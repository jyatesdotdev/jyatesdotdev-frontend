I rebuilt my portfolio site as a fully serverless application on AWS, replacing a Next.js app on Vercel. This post documents the journey: the architecture decisions, the bugs I hit in production, and the operational hardening that followed. If you're considering a similar setup — or just curious about what it takes to run a real application on AWS without servers — this is the full story.

### Why Leave Vercel?

Vercel is excellent for getting a Next.js site online quickly. But I wanted more control over the infrastructure, deeper AWS experience, and the satisfaction of owning every layer of the stack. I also wanted to prove that a personal site could run on AWS for pennies, with infrastructure-as-code managing everything.

The goal was simple: a portfolio site with a blog, interactive features (likes, comments, contact form), and zero servers to manage. Every resource would be defined in Terraform, deployed via GitHub Actions with OIDC — no static credentials anywhere.

### The Architecture

The site is split across four repositories, each with a clear responsibility:

- **jyatesdotdev-frontend** — a React SPA built with React Router 7 and Vite, prerendered to static HTML at build time
- **jyatesdotdev-api** — four Go Lambda functions handling interactions, contact, admin, and authorization
- **jyatesdotdev-infra** — Terraform managing all AWS resources
- **A private bootstrap repo** — account-level resources (OIDC provider, deploy IAM role, state and artifact buckets) that need to exist before anything else can be deployed

This separation matters. The bootstrap repo avoids a chicken-and-egg problem: you can't deploy Terraform if the state bucket and deploy role don't exist yet. Keeping it private also means the scoped IAM policies never appear in a public repository.

### The CloudFront Puzzle

CloudFront sits at the center of everything, and getting it right required solving several interrelated problems.

The first challenge was SPA routing. When a user navigates to `/projects`, S3 doesn't have a file at that path — it has `/projects/index.html` (generated by Vite's prerendering). A CloudFront Function rewrites these directory-like paths to append `/index.html`, making prerendered routes work. But this function had to be carefully scoped: it must *not* rewrite `/api/*` paths, or API requests would be silently redirected to the SPA.

```javascript
if (!uri.startsWith('/api/')) {
  // Rewrite for SPA prerendered routes
  if (uri.endsWith('/')) {
    request.uri += 'index.html';
  } else if (!uri.includes('.')) {
    request.uri += '/index.html';
  }
}
```

The second challenge was error handling. CloudFront's `custom_error_response` lets you return a fallback page for specific HTTP status codes — perfect for SPA routing, where any unmatched path should serve `index.html` and let the client-side router handle it. I initially configured fallbacks for both 403 and 404 errors. That was a mistake.

The problem: S3 returns 403 (not 404) when an object doesn't exist and the requester lacks `s3:ListBucket` permission. My custom error response for 403 was catching *all* 403s — including legitimate 403 responses from the API Lambda. A user hitting a rate limit or sending a bad request to the API would receive the SPA's HTML instead of the API's JSON error.

The fix had two parts. First, I added `s3:ListBucket` to the CloudFront origin access control's bucket policy, which makes S3 return 404 (not 403) for missing objects. Second, I removed the 403 custom error response entirely, keeping only the 404 fallback. Now API errors pass through correctly, and missing pages still get the SPA fallback.

### Debugging Production Bugs

With the infrastructure in place, I deployed the site and immediately hit a series of bugs that only manifested in production.

**Likes weren't toggling.** The like system uses IP-based deduplication — each IP can only like a post once, and clicking again removes the like. In production, every click created a new like instead of toggling. The issue was in how I extracted the client IP from the `X-Forwarded-For` header. CloudFront, API Gateway, and the Lambda proxy each append their own IP to the chain, so the header looks something like `203.0.113.1, 54.230.1.1, 10.0.0.1`. I was using the entire string as the deduplication key, but the trailing IPs change with every request. The fix was to extract only the first IP — the actual client:

```go
func extractIP(xff string) string {
    ip, _, _ := strings.Cut(xff, ",")
    return strings.TrimSpace(ip)
}
```

**The contact form was failing silently.** This turned out to be three issues stacked on top of each other. The frontend sent the reCAPTCHA token in a field called `recaptchaToken`, but the backend expected `token`. The frontend used the reCAPTCHA action `contact_form`, but the backend validated against `contact`. And the SES IAM policy was scoped too narrowly — SESv2's `SendEmail` action requires permission on both the identity resource and a wildcard message resource. Each fix was small, but finding them required tracing the request from the browser through CloudFront, API Gateway, Lambda, and SES.

**Comment likes were also failing** due to a similar reCAPTCHA action mismatch: the frontend sent `comment_like` but the backend expected `like_comment`. After fixing all four endpoints, I documented the action map to prevent future drift:

| Endpoint | Frontend Action | Backend Action |
|---|---|---|
| Like toggle | `like` | `like` |
| Comment create | `comment` | `comment` |
| Comment like | `comment_like` | `comment_like` |
| Contact form | `contact_form` | `contact_form` |

**The theme toggle was broken.** When the theme was set to "system," clicking the toggle did nothing visible because the code didn't resolve whether "system" meant dark or light. The fix added a `resolvedTheme` variable that checks `window.matchMedia('(prefers-color-scheme: dark)')` and listens for changes, so the toggle always knows the current effective theme.

### Security Scanning and Supply Chain Lessons

Making the infrastructure and API repositories public meant I needed automated security scanning. I started with tfsec for Terraform, but it's deprecated. I switched to Trivy — and then discovered that Trivy had suffered a supply chain compromise in March 2026. I ultimately settled on Checkov for Terraform IaC scanning, and CodeQL for the Go API and TypeScript frontend.

The lesson: even your security tools can be compromised. Pin versions, verify checksums, and don't assume a tool is safe just because it's popular.

Before making the repos public, I audited every file for secrets and resource identifiers. The admin username was moved from a Terraform variable default to a GitHub Secret. Resource IDs (account number, bucket names, distribution IDs) were redacted from READMEs. The bootstrap repo — which contains the IAM policies defining what the deploy role can do — stays private.

### Observability with CloudWatch RUM

I wanted real user monitoring without a third-party service. CloudWatch RUM provides performance metrics, error tracking, and HTTP request monitoring — all feeding into the same AWS console I use for everything else.

The setup requires a Cognito Identity Pool configured for unauthenticated access. This gives the browser SDK temporary AWS credentials scoped to a single permission: `rum:PutRumEvents`. The SDK loads lazily — it's only imported on pages that render the `Analytics` component, so there's no bundle cost on pages that don't need it.

I initially set the sampling rate to 10%, which seemed reasonable. After deploying, I saw zero events in the RUM console. With low traffic, a 10% sample rate means most sessions are silently dropped before any data is sent. The sampling decision happens client-side — the SDK rolls a random number and skips the entire session if it loses. I bumped it to 100%. For a personal site with minimal traffic, the cost is negligible and I actually get data.

RUM automatically captures geographic information from the client IP — country, subdivision, and city — which appears in the event metadata without any additional configuration.

### Cost Protection: The Budget Guard

Running at 100% sampling raised a question: what happens if a page goes viral? CloudWatch RUM costs $1 per 100,000 events, and each page load generates roughly 5-10 events. But the real risk is Cognito — the Identity Pool creates temporary credentials for each visitor, and beyond the 50,000 free tier MAUs, it's $0.0055 per user. A million visitors could mean thousands of dollars in Cognito charges alone.

AWS doesn't offer a native spending cap for RUM, so I built one. The budget guard is a Terraform module with four components:

1. **An AWS Budget** scoped specifically to the CloudWatch RUM service, with a $10/month limit
2. **A Budget Action** that automatically attaches a deny policy to the Cognito IAM role when the limit is exceeded — this blocks all `rum:PutRumEvents` calls at the IAM level
3. **A Lambda function** that detaches the deny policy, re-enabling RUM
4. **An EventBridge rule** that triggers the Lambda on the 1st of each month

The beauty of this approach is that it's a true hard stop. The deny policy is evaluated at the IAM layer, so even if the client-side SDK tries to send events, they're rejected. The SDK's error handler catches the failure silently — no user-facing impact. And the monthly reset is fully automatic.

### Lifecycle Rules and Operational Hygiene

With the site running, I added lifecycle rules to prevent unbounded storage growth:

| Bucket | Rule | Retention |
|---|---|---|
| Static site | Noncurrent version expiration | 30 days |
| Access logs | Object expiration | 90 days |
| Lambda artifacts | Object expiration | 14 days |

S3 versioning on the static site bucket means every deployment preserves the previous version. The 30-day retention gives a comfortable rollback window. Access logs expire after 90 days — long enough for trend analysis, short enough to keep costs near zero. Lambda artifacts expire after 14 days since they can always be rebuilt from source.

### Pipeline Design

The deployment pipeline uses GitHub Actions with OIDC authentication — no static AWS credentials stored anywhere. Each repository has its own workflow:

The **API workflow** builds the Go Lambda functions, uploads the zips to S3, and dispatches to the infra repository with the artifact locations. The **infra workflow** runs Terraform apply with those artifact parameters. The **frontend workflow** builds the SPA, syncs to S3, and invalidates the CloudFront cache. It doesn't touch Terraform at all.

A concurrency group on the infra workflow ensures only one Terraform apply runs at a time. Without this, parallel runs would race for the state lock, and the loser would fail with a lock error that required manual cleanup.

For manual infra deployments (when changing infrastructure without new Lambda code), you need to provide the current Lambda artifact keys explicitly. The latest artifacts can be found in S3:

```bash
aws s3 ls s3://<artifacts-bucket>/lambdas/ --region us-west-2
```

### What It Costs

After 18 days of running, the total cost was $0.009. The projected monthly cost is roughly $6.50, with WAF accounting for 77% of that. The breakdown:

- **WAF**: ~$5.00/month (fixed cost for the web ACL + rules)
- **Route53**: ~$0.50/month (hosted zone)
- **KMS**: ~$1.00/month (customer-managed key)
- **Everything else**: fractions of a cent (Lambda, DynamoDB, S3, CloudFront, API Gateway, RUM)

The KMS key is the one cost I'd reconsider. AWS-managed keys are free, and for a personal site, the additional control of a customer-managed key may not justify the dollar. But it's there, and it encrypts DynamoDB and CloudWatch Logs at rest.

### Lessons Learned

**Test the full request path, not just individual components.** The reCAPTCHA mismatches, the SES policy gaps, and the CloudFront error response issue all worked fine in isolation. They only broke when a real request traversed the entire chain from browser to backend.

**Error handling in CDNs is global by default.** CloudFront's custom error responses apply to the entire distribution, not per-origin. If you serve both a static site and an API from the same distribution, you need to be very deliberate about which errors trigger fallback behavior.

**Sampling rates need traffic context.** A 10% sample rate is reasonable for a site with thousands of daily visitors. For a personal site, it means you see nothing. Match the rate to your actual traffic volume.

**Security tools can be compromised too.** The Trivy supply chain incident was a reminder that dependencies in your CI pipeline deserve the same scrutiny as dependencies in your application code.

**Own the boring parts.** Lifecycle rules, concurrency groups, state lock cleanup procedures, rollback documentation — none of this is exciting, but it's what separates a demo from a production system. Even a personal site deserves operational hygiene.
